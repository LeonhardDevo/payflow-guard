# Foundation contract (web-core ⇄ web-ui ⇄ worker + RAG ⇄ e2e)

The platform foundation is built in parallel by several engineers, then cloned into
OpsBot and ScamPause. This file pins the seams between them. PLATFORM.md defines the
service contracts (§4); this file pins the **web app internals** (routes, Inertia pages,
props, file ownership) and the **product-neutral naming** that makes cloning easy.

## 0. Product-neutral naming

Foundation code must not mention "PayFlow" except through config:
- web: `config('app.name')`, `config('product.slug')`, `config('product.tagline')`, brand tokens in `resources/css/brand.css`,
  logo component `resources/js/components/brand/AppLogoMark.vue` (inline SVG, brand-specific, swapped per project).
- worker: `PRODUCT_NAME`, `PRODUCT_SLUG` env; bot strings use `{product}` placeholder.
- RAG (inside the worker): `PRODUCT_NAME` env; the system prompt template has a product/domain section loaded from
  `apps/worker/src/rag/prompts/domain.{ru,en}.md`.
Domain-specific features (invoices, documents of a niche, approvals…) are NOT part of the foundation.

Starter-kit specifics (Laravel 13 + Inertia 3 + `@inertiajs/vite` + Wayfinder + Fortify + passkeys, build tool **vite-plus** `vp`):
- The kit self-hosts fonts by **downloading from Bunny at build time** (`laravel-vite-plugin/fonts` `bunny(...)` + `@fonts` Blade directive). This violates the no-CDN rule → web-ui removes the `fonts:` option and the `@fonts` directive and uses `@fontsource-variable/*` imports in `resources/css/app.css`.
- `vite-plus` native binding for Windows is missing from the kit's lockfile; it was installed with `npm install --no-save @voidzero-dev/vite-plus-win32-x64-msvc@0.3.0`. web-ui must make this durable (e.g. add it to `optionalDependencies` alongside the linux one) so `npm ci` works on Windows and Linux CI.
- Layouts are assigned in `resources/js/app.ts` by page-name prefix; `marketing/*`, `dev/*`, `invitations/*` pages must get the right layout (marketing layout / no app shell).
- Typed routes: use Wayfinder (`@/routes`, `@/actions`) in Vue instead of hard-coded URLs; regenerate after route changes.

Both may *read* everything. If web-ui needs a backend change (new prop, new route), it asks web-core instead of
editing PHP; web-core does the same in the other direction.

## 4c. Payments & markets (PLATFORM.md §11) — foundation step F3

**Markets.** `MarketResolver` maps country/currency to a gateway (`RU`/`RUB` → `yookassa`, otherwise `stripe`);
`BILLING_DRIVER=fake|stripe|yookassa` forces one gateway, `market` uses the mapping. A gateway is *available* only when its
class exists and its required config is set (`billing.gateway_requirements`, e.g. `YOOKASSA_SHOP_ID` + `YOOKASSA_SECRET_KEY`);
`fake` is never available outside `BILLING_DRIVER=fake`. Visitor defaults (`/pricing`, onboarding) and
`billingCurrencies()` only offer markets whose gateway is available. Production refuses to boot with `BILLING_DRIVER=yookassa`
and missing credentials.

**Subscription lifecycle.** Change plan, cancel, resume and portal use the gateway the live subscription was created on
(`subscriptions.gateway`), never the workspace's current market. `PATCH /settings/workspace` rejects a country/currency change
that would move a live subscription to another gateway (`billing.errors.market_locked_by_subscription`).

**Idempotency.** Stripe keys derive from the intent: checkout `checkout-{ws}-{plan}-{interval}-{currency}-{customer}-{10-min bucket}`,
change/cancel/resume `{op}-{subscription}-{last_event_at}-{1-min bucket}`, portal configuration updates by params hash. YooKassa
uses `Idempotence-Key` (≤ 64 chars) built the same way; renewals `renewal-{subscription}-{period_end}-{retry bucket}`.

**YooKassa (RU).** `App\Billing\YooKassa\YooKassaClient` (REST v3, Basic `shopId:secretKey`), `YooKassaGateway`
(first payment with `save_payment_method: true` and redirect confirmation; 54-ФЗ `receipt` when `YOOKASSA_RECEIPTS=true`;
plan changes are scheduled for the next period; cancel/resume are local), `YooKassaPaymentProcessor` (re-fetches every payment
by id before trusting it; idempotent by payment id; underpaid or foreign payments are ignored), `YooKassaRenewals`
(charges the saved `payment_method_id` when the period ends; a failed charge sets `past_due` + one e-mail, retries every
`YOOKASSA_RETRY_HOURS`, cancels after `YOOKASSA_GRACE_DAYS`; `cancel_at_period_end` ends the subscription without a charge).
Recorded-shape fixtures: `contracts/yookassa/{payments,notifications}/*.json`.

**Client payments (`PaymentGateway`).** Drivers `stripe` (merchant restricted key → Price + Payment Link with metadata
`workspace_id`/`reference`, one completed session, webhook endpoint registered in the merchant account with its own signing
secret), `yookassa` (merchant shop credentials → redirect payment) and `fake` (offline, only with `BILLING_DRIVER=fake`).
Credentials live encrypted in `payment_accounts.credentials`; links in `payment_links` (`reference` is the domain key, e.g.
`invoice:42`). `PaymentLinks::create|refresh|deactivate|transition` enforce the status machine and dispatch
`App\Billing\Payments\PaymentLinkStatusChanged` after commit — domain code (PayFlow invoices) listens to it.
`PaymentAccounts::connectStripe|connectYooKassa` connect a workspace account (`PAYMENTS_WEBHOOK_BASE_URL` = public worker URL).

| Internal route (worker only) | Purpose |
|---|---|
| `POST /internal/v1/yookassa/notifications` | client payment → re-fetch with the merchant shop; subscription payment → `YooKassaPaymentProcessor` |
| `POST /internal/v1/billing/renewals` | due YooKassa renewals (scheduler) |

## 7. Extension points for domain code

Domain features plug in at these seams; foundation files outside them should not need edits.

**web (Laravel)**
- Abilities and roles: `config/permissions.php` (`abilities` catalog, `roles` → abilities, `*` = all) and the `App\Enums\WorkspaceRole` enum.
  Abilities are exposed to Vue as `can` (section 2) and registered as Gates. Role labels: `roles.<value>` in `lang/{en,ru}.json`.
- Answer actions and inline-button callbacks: implement `App\Assistant\Actions\AssistantAction`
  (`handle(AssistantActionContext): AssistantActionResult`) and register it in `config/product.php` under `assistant.actions` (type → class).
  One handler serves both channels: Telegram (`POST /internal/v1/telegram/actions`) and the web assistant (`POST /assistant/actions`).
  The foundation ships `EscalateAction`.
- Assistant empty-state questions: `config/product.php` → `assistant_suggestions` (per locale).
- Plans and limits: `config/billing.php`; the `plan.limit:<limit>` route middleware enforces a limit (`seats`, `documents`, `ai_queries_monthly`).
- Outbox: publish with `App\Outbox\Outbox` (singleton) inside the DB transaction; the worker routes the topic (see below).
- In-app notifications: `InAppMessage` kinds `info|success|warning|danger|ai`; they appear in the shared `notifications` prop.
- Dashboard: `DashboardController` returns placeholder `stats`; a product replaces the page and the controller.

**worker (Node, bot module registry)**
- `BotModule` (`src/bot/types.ts`): `{ name, commands?: BotCommand[], messages?: {en?, ru?}, register?(composer), actions?: Record<type, ActionHandler>, notifications?: Record<name, NotificationTemplate> }`.
  Add a module in `src/bot/modules/` and list it in `domainModules` (`src/bot/modules/index.ts`). Order is `core`, domain modules, then the catch-all `assistant`.
- `createRegistry(modules, translator)` returns `BotRegistry { modules, commands, action(type), notification(name) }`.
  Commands feed `/help` and the Telegram command menu (`descriptionKey` is an i18n key). Module `messages` merge into the bot i18n (`src/i18n/{en,ru}.json`).
- `telegram.notify` accepts `text_html` or `template` (+ `params`); `template` resolves through `registry.notification(name)`, and an unknown template is a permanent failure.
- Jobs: add the topic to `TOPIC_ROUTES` (`src/queues/routes.ts`, "domain" section) and its handler in `createHandlers()` (`src/jobs/index.ts`). The job name equals the outbox topic.

**RAG (TypeScript, `apps/worker/src/rag`, ADR-0014)**
- `Tool` (`src/rag/tools/types.ts`): `name`, `description`, `parameters` (JSON schema), `requiredPermission` (checked with `ChatUser.can`), `dataTool`,
  `run(ctx: ToolContext, args): Promise<ToolResult>` with `ToolResult { content, sources?, hasData?, actions?, confidence? }`. Throw `ToolError` for expected
  failures; the message is shown to the model. `ToolContext` carries `workspaceId`, `user`, `viewer`, `retriever`, `embedder`, `web` (signed client of
  the web internal API), `sources`, `topK`, `locale`, `requestId`.
- Register tools through `buildRegistry(extra: ToolRegistrar[])` (`src/rag/tools/index.ts`, `ToolRegistry.register`, duplicate names throw).
  `availableFor(user)` filters by permission.
- Deterministic `mock` provider routing: add `IntentRule { tool, patterns, buildArgs }` to `DOMAIN_RULES` (`src/rag/agent/intents.ts`). Real providers ignore these rules.
- Domain HTTP routes: `DOMAIN_ROUTES` in `src/rag/http/index.ts` (signed like every `/v1` route).
- Product and domain prompt: `src/rag/prompts/domain.{en,ru}.md` (the system prompts `system.{en,ru}.md` stay foundation).

**Identity** (product-neutral, section 0): `scripts/project.env` (name, slug, ports), `config/product.php`, `resources/css/brand.css`,
`AppLogoMark.vue`, worker `PRODUCT_NAME`/`PRODUCT_SLUG` (also used by the RAG prompts).
